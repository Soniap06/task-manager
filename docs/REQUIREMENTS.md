# Требования и этапы

Источник: «ТЗ_Курс_ТП.pdf», страницы 2–3, предоставленное командой 20 октября 2026 года. Название: «Разработка интеллектуальной системы управления задачами с автоматизацией цикла разработки через GitHub и LLM-агентов». Репозиторий в ТЗ: `https://github.com/Soniap06/task-manager.git`.

Ниже — рабочее изложение для общего контекста в git; исходный PDF остаётся первичным документом. PDF не копируется с личного компьютера и не нужен для повседневного запуска. ID и порядок этапов введены для разработки, в оригинале их нет. Статусы отражают исходный прототип, а не обещание реализации.

| ID | Требование ТЗ | Сейчас | Проверяемый результат реализации |
| --- | --- | --- | --- |
| R1 | Создание, редактирование и перемещение задач; Backlog, To Do, In Progress, Review, Done | Частично: генерация и стрелки, 3 колонки | Можно создать и изменить карточку, переместить её по пяти статусам |
| R2 | Профили: стек, квалификация, текущая загрузка, доступное время | Нет | Профили редактируются, планировщик получает компетенции и лимиты часов |
| R3 | LLM-декомпозиция, планирование спринта, распределение по компетенциям и лимитам часов, обогащение задач | Только генерация описания одной карточки | План содержит задачи, оценки и исполнителей; лимиты проверяются, нехватка ресурсов явно сообщается |
| R4 | Генерация имени и создание ветки при старте задачи, PR при переходе в Review через GitHub App | Частично: GitHub App создаёт ветку после явного подтверждения черновика (триггер уточнён пользователем); PR ещё нет | В GitHub появляются связанные ветка и PR; ошибки не отображаются как успех |
| R5 | Автоматическое review входящих PR с комментариями в GitHub | Нет | Событие PR запускает анализ; замечания публикуются к соответствующей версии diff |
| R6 | Встроенный AI-исполнитель для типовых задач: тесты и документация | Нет | На выбранной задаче получается проверяемый diff тестов/документации с результатами проверок |
| R7 | Исходный код, пояснительная записка и демонстрация работы на защите | Код прототипа | Есть воспроизводимый запуск, записка и сценарий демонстрации основных модулей |

Входы из ТЗ: описания бэклога и предметной области, профили участников, webhook-события `push`, `pull_request`, `pull_request_review`. Выходы: доска, планировщик, сервис веток/PR, review с публикацией комментариев, записка и исходники.

## Уточнение пользователя: подключаемые проекты (20 октября 2026)

Расширение R4, обозначение **R4-PROJECTS**: Task Manager подключается к существующим GitHub-репозиториям и позволяет менять рабочий проект через интерфейс. Нужны выбор из доступных репозиториев, подключение по GitHub-ссылке, отдельная доска каждого проекта и неизменность привязки созданной задачи к исходному репозиторию. Роли пока не учитываются. Это запрос пользователя сверх исходного ТЗ; подключение проектов реализовано в текущих изменениях по [обновлённому плану](plans/R4-create-task-branch.md). Загрузка ZIP не входит в первую версию: она не предоставляет доступа для создания GitHub-веток.

## Предлагаемая последовательность

Это бэклог для выбора отдельных задач, а не команда агенту выполнять его целиком.

1. **Основа.** Вынести общий LLM-клиент из локального конфига; определить контракт задачи и стратегию хранения. Исправить раздачу файлов перед публикацией. Добавить поведенческие проверки с заглушкой LLM.
2. **Доска и данные (R1).** Пять статусов, редактирование; реализовать хранение после выбора архитектуры. Сохранность при перезагрузке — предложенный инженерный критерий, явно не описанный в ТЗ.
3. **Команда и спринт (R2–R3).** Профили, оценки часов, спринт, планирование. Ограничения проверяются кодом, а не только промптом. Отсутствующие компетенции и превышение нагрузки имеют явный результат.
4. **GitHub App (R4).** Контракты и тестовые события, затем установка App и серверная аутентификация, создание ветки и PR. Добавить проверку подписи webhook, защиту от повторной доставки и хранение связи задача/ветка/PR.
5. **Автоматическое review (R5).** Получение актуального diff, структурированный результат LLM, привязка к строкам и публикация; защита от устаревших и повторных комментариев.
6. **AI-исполнитель (R6).** Ограниченная область файлов и задач, изолированное выполнение, diff и проверки до применения результата.
7. **Защита (R7).** Записка и демонстрационный сценарий с проверкой работы всех модулей; материалы собирать по мере разработки.

Проверка webhook, повторов, секретов и валидация LLM — предложенные инженерные условия надёжности, а не дословные пункты ТЗ. Детальные критерии и распределение ответственности фиксируются в конкретной задаче/плане.
