На Mac установлен local.task-manager.maintenance: каждый час и при входе запускает ~/Library/Application Support/TaskManager/mac-maintenance.py через установленный Python 3.14. Через существующий SSH-ключ скачивает только новый архив в backups/vps-daily в той же папке, проверяет SHA-256, JSON v2, SQLite integrity/FK в отдельном временном каталоге. Частичный файл не становится успешным архивом, tar не распаковывается произвольными путями. Исходные карточки и база не изменяются. Локальные архивы/отчёт 600, каталог 700. Если Mac выключен или SSH-ключ недоступен, скачивание пропускается до следующего запуска; серверные копии продолжаются. Это внешний по отношению к VPS диск, но не независимое круглосуточное облачное хранилище. Не публиковать архивы: они содержат пароль доски, SESSION_SECRET и PEM. ## Мониторинг

Тот же локальный скрипт проверяет HTTPS health (с TLS-проверкой и повторами), диск через SSH df и свежесть backup (48 часов). Порог: занято 80% или свободно менее 2 ГБ. Отчёт ~/Library/Application Support/TaskManager/maintenance-status.json, логи ~/Library/Logs/TaskManager/maintenance*.log. В отчёт не попадают содержимое карточек и секреты. Он показывает последнюю выполненную проверку, не непрерывную доступность.

Создана почасовая автоматизация Codex «Контроль Task Manager VPS» (task-manager-vps): читает отчёт/запускает проверку, сообщает только новый сбой, ухудшение, восстановление либо необходимое действие; сервер сама не меняет. Для неё нужен работающий Codex на Mac. При выключенном Mac независимого внешнего оповещения нет.

Диагностика на Mac:

```bash
launchctl print gui/$(id -u)/local.task-manager.maintenance
python3 "$HOME/Library/Application Support/TaskManager/mac-maintenance.py"
```

На VPS (через существующий SSH): systemctl is-active task-manager caddy; systemctl list-timers task-manager-backup.timer; df -h /. Привилегированные логи: sudo journalctl -u task-manager или -u caddy. Не выводить env и PEM. Сетевые таймауты иногда встречались, одна успешная проверка не гарантирует постоянную доступность.

## Обновление приложения

1. В checkout получить remote через fetch, выбрать проверенный commit задачи/PR, посмотреть diff и совместимость с изменениями Софии. В рабочем checkout: npm run check, npm test; для ops — python3 -m unittest discover -s test -p 'test_vps*.py' и bash -n изменённых shell-скриптов. Не выкатывать незакоммиченные файлы без фиксации точного diff.
2. Упаковать конкретный commit через git archive в локальный архив исходников; никаких .env, ai.config.json, PEM, .data или рабочих архивов в пакет. Загрузить в домашний каталог karina; сравнить SHA-256 до применения. Не делать git pull поверх root-каталога /opt/task-manager.
3. На VPS выполнить проверенный backup и убедиться, что внешний архив скачан. Сохранить текущую версию /opt/task-manager и конфигурацию как rollback. Новую версию подготовить в отдельном каталоге, перенести существующий ai.config.json (не пример), выставить root:task-manager и доступ только на чтение. server.env/github.env/PEM и DATA_DIR не заменять конфигурацией разработчика.
4. При несовместимой схеме или миграциях сначала отдельный план и проверка восстановления. Нельзя откатывать старый код на новую несовместимую БД. Автоматической миграции рабочих задач этим пакетом нет.
5. Для переключения остановить только task-manager, заменить каталог приложения подготовленным release, запустить сервис. Не запускать два процесса с одним DATA_DIR. Caddy/DNS/SSH/firewall при обычном обновлении не меняются. Не трогать пользовательский checkout Софии или старый local.task-manager на Mac.
6. Проверить systemd, локальный и публичный health, HTTPS login, 401 без cookie, вход и чтение существующих карточек, GitHub read-only check. Генерацию Qwen проверять без создания карточек/веток. Не запускать старые configure.sh/public-https.sh/rename-domain.sh как скрипты обычного обновления.
7. При ошибке остановить сервис, вернуть предыдущий каталог и запустить. Живые данные не восстанавливать автоматически поверх новых пользовательских изменений. Записать commit, результат и rollback в план. Текущая процедура требует контролируемого sudo, CI/CD и универсальный deploy-скрипт не реализованы.
