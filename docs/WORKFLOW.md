# Работа вдвоём с Codex

## Начало работы

1. Установить Node.js 24 (версия записана в `.nvmrc`; при наличии nvm выполнить `nvm use`). Зависимостей npm пока нет, `npm install` не требуется.
2. Выполнить `npm run setup`, затем `npm run check`. Setup создаёт `.env` и `ai.config.json` из соответствующих примеров только при отсутствии; существующие настройки сохраняются. Для поведенческих проверок выполните `npm test`.
3. Запустить `npm start` и открыть `http://127.0.0.1:3000`. Для генерации запустить сервер LM Studio на порту 1234 и указать модель и endpoint в `ai.config.json`. Для веток заполнить GitHub App по README и подключить рабочий репозиторий через интерфейс; ключ остаётся локально.
4. Открыть репозиторий в Codex. Корневой `AGENTS.md` содержит инструкции; остальные документы он читает по необходимости. При добавлении инструкций в уже открытый чат попросить перечитать `AGENTS.md` или начать новый чат.

Токены GitHub или платных LLM не нужны для настройки harness и синтаксических проверок. Если позже потребуются интеграции, настройка секретов должна быть отдельным явным шагом.

## Одна задача

Карина и София выбирают разные задачи, назначают владельца и второго участника на review. Перед стартом указывают затрагиваемые файлы: сейчас особенно легко пересечься в `script.js` и `server.js`.

Работайте в отдельных клонах или worktree, каждый со своей веткой от актуальной общей базы. Изменения в одном checkout видны всем чатам, поэтому параллельная работа разных чатов в нём не изолирована. Локальный `.env`, PEM и `.data` в новый worktree автоматически не переносятся: там тоже нужен setup и отдельная конфигурация. Для нескольких серверов задавайте разные PORT и DATA_DIR; один каталог блокируется одним процессом.

Перед началом, особенно после перерыва или в новом чате, проверьте `git status --short`, текущую ветку и `git branch -vv`, выполните `git fetch --all --prune` и сравните новые коммиты/diff своей ветки и целевой ветки PR. Учитывайте изменения коллеги, перечитайте изменившиеся инструкции и план задачи. При недоступной сети укажите, что актуальность remote не подтверждена; не заменяйте проверку слепым `git pull`.

Для каждой крупной задачи сначала найдите существующую незавершённую ветку по её плану/PR и продолжайте в ней; при наличии только удалённой ветки создайте локальную tracking-ветку. Если ветки под задачу нет, создайте `codex/<task-id>-<description>` от проверенной актуальной базы. Не создавайте дубликаты и не используйте ветку другой задачи или уже слитой работы. Незакоммиченные изменения сохраняйте перед переключением; отдельный worktree позволяет не смешивать задачи. Не используйте `reset --hard` или `clean` для освобождения рабочего дерева. Роли участников меняются по задачам; постоянное разделение frontend/backend не требуется.

Большой задаче нужен план по [шаблону](plans/TEMPLATE.md). Маленькой достаточно критериев в issue. Согласование архитектуры нужно при отсутствии влияющего на результат решения; дополнительное разрешение на каждый обычный шаг не требуется.

## Проверка перед PR

- `npm run check`: JS-синтаксис всех отслеживаемых и новых JS-файлов вне игнорируемых каталогов, плюс наличие локальных ресурсов из `index.html` и `projects.html`. Это не тест корректности поведения.
- `git diff --check`: пробелы и ошибки патча. Для новых файлов сначала проверьте их содержимое отдельно, поскольку обычный diff их не показывает.
- Изменение UI: открыть страницу; проверить обычный и узкий экран, пустой ввод, Enter и кнопку, переносы в обе стороны и границы доски. При наличии LLM проверить успешную генерацию, при отключённом сервисе — ошибку и восстановление кнопки. Проверить восстановление карточек и колонок после перезагрузки; ссылка должна вести в настроенный репозиторий. Подготовка создаёт только черновик. Проверить режим «Без ИИ», вопросы и ответы, ручное редактирование, ошибку модели и отдельное подтверждение. Именно подтверждение реально создаёт удалённую ветку: для ручных экспериментов выбирайте подходящую тестовую задачу.
- Изменение LLM: использовать воспроизводимые заглушки для валидного ответа, неверного JSON/полей и ошибки сервиса; реальную модель проверять отдельно, когда она доступна. Для работы с GitHub аналогично использовать fixtures без токенов. Для отдельной проверки реальной Qwen запустить `npm run llm:check`: она не создаёт карточек или веток и требует ручной оценки содержания ответа.
- `npm test`: автоматические проверки на `node:test` с заглушками GitHub/LLM, включая HTTP и логику UI. Для новой логики добавить тесты результата и ошибок. `npm run github:check` — отдельная реальная проверка авторизации и списка репозиториев без создания веток; секреты нужны только для неё и настоящих операций GitHub.

В PR указать связанное требование, изменение поведения, выполненные команды и ручные проверки, ограничения. Если LM Studio или GitHub недоступны, прямо написать, какие сценарии не проверены. Второй участник смотрит diff и запускает относящиеся к задаче проверки. Merge выполняется по принятому командой процессу; harness не меняет настройки защиты веток на GitHub.

## Передача незавершённой задачи

В плане задачи или PR оставить: ветку и исходную базу, что сделано, затронутые файлы, результаты проверок, открытые решения и ближайший конкретный шаг. Не складывать всё в один общий постоянно редактируемый журнал. Обновлять `PROJECT.md` и статусы требований, когда поведение действительно изменилось.

## Примеры поручений

**Разработка:** «Прочитай AGENTS.md. Реализуй R1: добавить Backlog и Done, без изменения хранения и LLM. Критерии: пять колонок, перенос стрелками по порядку, границы не выходят за доску, адаптивность сохранена. Проверь и подготовь diff».

**Планирование:** «Прочитай AGENTS.md и R2–R3. Подготовь план профилей и планировщика, отдели требования ТЗ от предложений. Пока не реализуй».

**Review:** «Проверь diff этой ветки относительно согласованной базы. Найди ошибки поведения и риски потери данных; укажи сценарии и строки. Код пока не меняй».
