## Реализовано

Подготовка задачи сохраняет черновик. В опубликованной версии Qwen предлагает заголовок, описание и до трёх вопросов; технические планы, критерии и ветки ей не поручаются. Исходный запрос сохраняется отдельно. В опубликованной версии ответы сохраняются без повторного анализа. Локально в codex/r3-multistep-grilling (база b6b8ffd, 5 ноября 2026) добавлено grilling=true: 9–30 вопросов суммарно, 3–5 в раунде, 1–2 в последнем, история и текущий черновик передаются Qwen, затем отдельное подтверждение. Границы и ревизии проверяет код. Новая форма включает режим, старые клиенты/карточки совместимы; при ошибке доступно явное ручное подтверждение. На VPS эта версия ещё не установлена. Пользователь редактирует текст и отвечает на вопросы, после чего подтверждает создание GitHub-ветки. Тип выбирается в интерфейсе, в опубликованной версии имя формируется кодом: feat/fix/chore и UUID; новый локальный формат описан ниже. При недоступной модели можно заполнить карточку вручную или заранее выбрать «Без ИИ». Повторные подтверждения идемпотентны; устаревшие ответы другой вкладки отклоняются по draftRevision. Прежние карточки с критериями/шагами и существующие ветки сохранены. Подробности по-прежнему открываются только в диалоге.


Повтор с тем же request ID не создаёт новую задачу. При потерянном ответе GitHub проверяется точный ref. При перезапуске сервер сверяет незавершённые попытки, дошедшие до GitHub. Чужие и изменённые ветки не перезаписываются, локальный checkout не переключается. Публичные файлы ограничены HTML/CSS/JS интерфейса; секреты и данные не раздаются, CORS `*` удалён.

GitHub App имеет доступ к `karinalien/habit-tracker` и ранее разрешённому репозиторию исходников `karinalien/task-manager`. Первый рабочий подключённый проект — трекер привычек; новые ветки для него создаются в отдельном репозитории.

Реализованы каталог доступных App репозиториев, подключение по ссылке/списку, выбор базы, отдельные доски, смена проекта и локальное архивирование подключения. Снимок repository/installation/base хранится у каждой задачи; ID проекта передаётся явно. Токены записи ограничены repository ID, кэш разделён по scope. Текущий формат JSON — версия 2, миграция версии 1 сохраняет резервную копию и не угадывает проект старых задач.

Подготовлена отдельная SQLite `.data/task-manager.sqlite` с users/projects/employees/tasks/events и скриптом `npm run db:init`. Теперь сотрудники и события подключены к API; рабочие задачи остаются в JSON. [Схема и ограничения](DATABASE.md).

В коммите `0188841` (задача `codex/r3-qwen-planning`, опубликована в составе `codex/ui-sofia-style`) реализованы ai.config.json, упрощённый контракт Qwen, редактор и подтверждение. Проверки: npm run check, 95/95 автоматических тестов, UI на 320/375/1280 px и шесть реальных ответов Qwen с корректным контрактом. Смысловые ограничения описаны в [плане R3](plans/R3-qwen-planning.md). Модель может задавать лишние вопросы или неточно пересказывать запрос, поэтому описание доступно для правки, а исходные требования хранятся неизменно. GitHub-запись не зависит от полей модели и начинается только по подтверждению пользователя.

Доска и страница проектов приведены к оформлению Софии в ветке `codex/ui-sofia-style`: общий визуальный слой, верхняя навигация, белые колонки и панели, розовые карточки. Сохранены рабочие контроллеры и отображение подробностей только в диалоге; счётчики показывают видимые карточки. [План и проверки](plans/UI-sofia-style.md). R3 сохранена отдельным коммитом `0188841` и входит в историю ветки оформления. Перед публикацией проверена совместимость с актуальным `upstream/main` (`36fdfa9`): ветка включает изменения Софии, новые коммиты не обнаружены, 95/95 тестов проходят.

Начальные профили команды уточнены по работе в проекте: Карина — интеграции GitHub и ИИ (JavaScript, Node.js, Git/GitHub, GitHub App/REST API, Qwen/LM Studio, интеграционное тестирование); София — интерфейс и Backend (HTML/CSS, JavaScript, UI/UX, Node.js, SQLite, REST API, авторизация). При запуске заменяются только прежние стандартные роли/навыки; персональные правки, ID, назначения и ёмкость сохраняются. Эти метки описывают вклад в учебный проект, а не подтверждённый профессиональный грейд.

## Ограничения и следующие задачи

- Ветка R1 с пятью колонками и редактированием карточек локальная и ещё не опубликована; проверки на общей доске не было. Редактирование профилей, регистрация/роли, спринты и алгоритм распределения не реализованы.
- Нет создания PR, автоматического review и AI-исполнителя. Публичная доставка webhook не настроена.
- На VPS работает общая доска за HTTPS-прокси; приложение слушает loopback. Данные остаются в JSON/SQLite и доступны одному экземпляру сервера; отдельные локальные запуски имеют независимые доски.
- Для публичной доски настроен обязательный общий вход и базовые ограничения запросов. Регистрации, отдельных учётных записей и ролей нет; эксплуатационные ограничения и резервное копирование описаны в [VPS.md](VPS.md).
- После аварии генерация без сохранённого результата требует явного повтора. При конфликте существующей ветки требуется ручной разбор; автоматического удаления или переименования веток нет.
- В `.env` хранятся настройки App и необязательный ключ ИИ, в `ai.config.json` — подключение к модели; рабочие repo/base выбираются в интерфейсе. Личный `ai-api.js` сохранён, но не исполняется; документация прежнего клиента не описывает текущий запуск.
- Модель должна быть запущена в LM Studio; отказ модели не теряет сохранённую карточку. В новом примере конфигурации генерация ограничена 300 секундами для длинного интервью; существующий ai.config.json сохраняет свой timeoutMs. GitHub-запросы — 15 секундами каждый.
- Автоматические тесты используют заглушки. Реальные проверки и их ограничения фиксируются в плане R4.
