# Заготовка базы данных (DATA-1.1)

Выбрана SQLite через встроенный `node:sqlite` в Node.js 24. Дополнительных зависимостей, сервера БД и ORM нет. Проверено на Node.js 24.14.1 / SQLite 3.51.2. В этой версии Node.js модуль выводит предупреждение `ExperimentalWarning`; проект закрепляет Node.js 24.

База пока **не подключена к API и интерфейсу**. Работающие задачи и подключённые проекты продолжают храниться в существующем JSON-хранилище. Инициализация не переносит и не удаляет эти данные. Пустая SQLite-база подготовлена для последующего этапа.

## Инициализация

```sh
npm run db:init
# Другой путь (необязательный аргумент):
npm run db:init -- /absolute/path/task-manager.sqlite
# Проверки без внешних сервисов:
node --test test/database.test.js
```

Без аргумента используется `.data/task-manager.sqlite` в корне проекта; значение `DATA_DIR` текущего JSON-хранилища на эту заготовку не влияет. Каталог `.data/` игнорируется Git. Его содержимое не должно раздаваться HTTP-сервером. Не храните рабочую базу внутри публичных статических каталогов.

Схема находится в `db/migrations/001-initial.sql`. `lib/database.js` экспортирует `openDatabase(filename)` и `DEFAULT_DATABASE_PATH`. Соединение возвращается после инициализации; вызывающий код обязан закрыть его через `database.close()` в `finally`. Для временной базы поддерживается `openDatabase(":memory:")`.

На каждом соединении включаются `foreign_keys = ON` и ожидание блокировки `busy_timeout = 5000`. Миграции выполняются одной транзакцией `BEGIN IMMEDIATE`; применённая версия хранится в `PRAGMA user_version`. Повторный запуск сохраняет записи. Более новая неизвестная версия отвергается без понижения. Новые миграции добавляются отдельными файлами и в конец списка `MIGRATIONS` в `lib/database.js`; применённые SQL-файлы не изменяются.

## Сущности и ограничения

Все внутренние `id` — обязательные непустые `TEXT`, рассчитанные на UUID от приложения (`crypto.randomUUID()`). База не генерирует и не проверяет формат UUID. Это позволяет сохранить существующие UUID задач и проектов при будущей миграции. Числовые GitHub ID хранятся отдельно. Все таблицы `STRICT`: несовместимые типы данных отвергаются.

| Таблица | Поля и назначение |
|---|---|
| `users` | `id`, обязательное `display_name`, необязательный уникальный `github_login`, `created_at`. Заготовка пользователей без паролей, сессий и реализации авторизации. |
| `projects` | `id`, уникальный положительный `github_repository_id`, положительный `installation_id`, непустые `owner`, `name`, `base_branch`, `created_at`. Пара `owner/name` уникальна без учёта регистра. |
| `employees` | `id`, необязательный уникальный `user_id`, обязательные `name`, `role`, `executor_type`, `stack`, `capacity`, необязательный `avatar_url`, `created_at`. Сотрудник и пользователь — разные сущности; у AI-исполнителя учётная запись не требуется. |
| `tasks` | `id`, обязательный `project_id`, непустой `title`, `description` (по умолчанию пустая строка), `status`, необязательные `branch`, `pr_url`, `assignee_id`, `created_at`. |
| `events` | `id`, обязательный `project_id`, непустой `event_type`, обязательный `payload_summary`, `created_at`. Тип события свободный: например, `push`, `pull_request`, `pull_request_review`. Вебхуки пока не реализованы. |

`employees.executor_type` принимает только `human` или `ai_agent`. `stack` — JSON-массив в текстовой колонке, по умолчанию `[]`; будущий API должен отдельно проверить строковые элементы навыков. `capacity` — целое число **часов на спринт**, не меньше нуля (по умолчанию 0). Продолжительность спринта и распределение нагрузки пока не реализованы.

`tasks.status` допускает только `todo`, `progress`, `review`; по умолчанию `todo`. `branch` может быть `NULL`, но не пустой строкой. URL, GitHub-имена и имена веток должны дополнительно проверяться будущим API; SQL проверяет типы и базовую целостность.

Связи:

- `employees.user_id → users.id`: при удалении пользователя связь становится `NULL`, сотрудник сохраняется.
- `tasks.assignee_id → employees.id`: при удалении сотрудника задача остаётся без исполнителя.
- `tasks.project_id → projects.id` и `events.project_id → projects.id`: удаление проекта с задачами или событиями запрещено. Переключение проекта не меняет эти связи.

Время хранится текстом UTC в формате `YYYY-MM-DDTHH:MM:SS.sssZ`, по умолчанию формируется SQLite. Есть индексы для задач по проекту/статусу, исполнителю и событий по проекту/времени.

## Проверки и следующий этап

Проверены повторная инициализация файла, сохранение записей после переоткрытия, все таблицы, `integrity_check`, FK на новых соединениях, отсутствие осиротевших ссылок, поведение удаления, допустимые статусы, ограничения JSON и capacity, уникальность репозитория, UTC, rollback при ошибке и отказ от downgrade.

Далее потребуется отдельно спроектировать миграцию рабочего JSON, расширить поля задач данными генерации и повторов GitHub, заменить хранилище API, добавить операции сотрудников и пользователей. Эту SQLite-базу нельзя считать уже подключённым хранилищем приложения или системой авторизации. До миграции необходимо делать резервные копии JSON и SQLite; незаметного объединения двух источников данных нет.
