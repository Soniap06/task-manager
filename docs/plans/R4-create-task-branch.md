## Результат и границы

Task Manager — отдельное управляющее приложение. Пользователь подключает уже существующие GitHub-репозитории, выбирает рабочий проект и видит его доску. Каждая новая задача принадлежит выбранному проекту; после генерации описания сервер создаёт ветку именно в связанном репозитории. Можно переключаться между проектами без изменения `.env`, перезапуска сервера и потери старых карточек.

Первая версия рассчитана на один доверенный локальный контекст пользователя и одну настроенную установку GitHub App, имеющую доступ к нескольким репозиториям. Схема хранения предусматривает installation ID у каждого проекта. Подключение нескольких аккаунтов/организаций и пользовательский OAuth — отдельный следующий этап, а не условие смены репозитория внутри текущего аккаунта. Роли пока не реализуются.

Не входят: создание новых репозиториев из Task Manager, загрузка ZIP/локальных каталогов, клонирование и исполнение чужого кода, PR, review, webhooks, полное планирование спринта и публичное размещение. Локальный checkout Task Manager не переключается на ветку подключённого проекта. Ветка создаётся через GitHub API без загрузки всего репозитория на сервер.

## Подключение проекта: предлагаемый UX

1. На первом запуске показать пустое состояние «Подключите проект», а не ошибку из-за отсутствия GITHUB_OWNER/GITHUB_REPO.
2. Кнопка «Подключить репозиторий» открывает список репозиториев, доступных настроенной App: имя, владелец, описание, приватность и доступность записи. Есть поиск, обновление списка и обработка нескольких страниц GitHub API.
3. Второй способ — вставить `https://github.com/owner/repo` (можно с `.git`). Сервер разбирает ссылку и проверяет доступ через ту же App. Это подключение удалённого репозитория, не импорт его файлов.
4. Если App ещё не имеет доступа, показать объяснение и ссылку «Настроить доступ на GitHub». Пользователь выбирает нужные репозитории в настройках установки и возвращается нажать «Обновить». Task Manager сам не расширяет права.
5. После выбора показать owner/name и базовую ветку. По умолчанию использовать фактическую `default_branch` из GitHub, а не предполагать `main`; при желании выбрать другую существующую ветку.
6. «Подключить» сохраняет проект в Task Manager; само подключение и открытие доски не создают GitHub-веток. Первый раз репозиторий должен иметь хотя бы один коммит. Пустой, архивный, отключённый или недоступный для записи репозиторий нельзя использовать для создания веток; причина показывается явно.
7. В шапке доски — список подключённых проектов, точный `owner/repo`, базовая ветка и «Подключить ещё». Переключение меняет показанную доску. При перезагрузке восстанавливается выбор этой вкладки, если проект всё ещё доступен.
8. При нажатии «Создать задачу и ветку» зафиксировать project ID. Смена выбранного проекта во время долгой генерации не должна переносить результат на другую доску. В карточке/деталях показывать её собственный репозиторий и ветку.
9. Отключение проекта в Task Manager архивирует локальное подключение, запрещает новые внешние операции, но сохраняет историю задач. Оно не удаляет GitHub-репозиторий, ветки и установку App. Изменение доступа App — отдельное действие в GitHub.

### Список репозиториев и доступ

Для первой версии использовать `GET /installation/repositories`. Это список доступных App репозиториев, а не всех репозиториев, видимых пользователю в браузере. В интерфейсе честно писать «Доступные GitHub App репозитории».

Загрузка списка использует installation token без ограничения одним repository ID; запрашивать минимально необходимые права чтения и держать токен на сервере. Операция создания ветки получает другой token с `repository_ids: [repositoryId]` и `contents:write`. Кэш токенов разделять по installation ID, набору repo IDs и permissions: токен проекта A не должен использоваться для проекта B. Учитывать срок жизни, обновление и отзыв доступа.

Для отображения полного персонального каталога, включая репозитории без доступа App, потребуется отдельная авторизация пользователя GitHub и проверка его доступа. Это можно добавить следующим этапом; отсутствие ролей в Task Manager не отменяет авторизацию на стороне GitHub. В первой версии ограниченный список плюс подключение по ссылке и настройка установки покрывают основной сценарий.

### Почему не загрузка ZIP

ZIP и обычная папка содержат файлы, но не предоставляют GitHub-доступ, installation ID и надёжную историю refs. Для текущей задачи такой импорт не даёт возможности создавать удалённые ветки. Если в будущем нужен импорт локального проекта, он оформляется отдельной функцией: создание/выбор remote, публикация исходников и права. Скачивание или исполнение произвольного кода для выбора репозитория не требуется.

## Модель данных и неизменность назначения задач

**Project:** `id`, `repositoryId` (числовой ID GitHub), `installationId`, `owner`, `name`, `fullName`, `htmlUrl`, `defaultBranch`, `baseBranch`, `description`, `archived`, временные метки. Для MVP одно подключение на repository ID; повторное подключение возвращает существующий проект. Числовой ID — основная идентичность; owner/name могут измениться при переименовании.

**Task:** существующие поля плюс обязательный `projectId`, `repositoryId`, `installationId` и снимок `repositoryFullName`, `baseBranch`, `baseSha`, точное имя созданной ветки. Сохраняется выбранный на момент начала операции репозиторий, а не текущий выбор в UI. Изменение базовой ветки проекта влияет только на новые задачи. Уже подготовленная попытка повторяется с прежними параметрами.

**Выбор проекта:** состояние вкладки браузера (`sessionStorage`), не глобальная переменная backend. Открытые вкладки могут работать с разными проектами. Браузер передаёт project ID; backend сам получает repo/installation из доверенного хранилища и повторно проверяет доступ.

**Хранилище:** сохранить текущую атомарную запись и блокировку одного процесса. Обновить JSON-схему до версии 2: проекты и задачи в одном атомарно заменяемом документе. Перед миграцией сделать локальную резервную копию. Старые задачи связывать только с подтверждённым репозиторием из сохранённых данных; неоднозначные записи показывать как «требуется привязка», без запросов записи в GitHub. Нельзя мигрировать все старые задачи в текущий выбранный проект.

**Повторы:** request ID связан с project ID и исходным содержимым задачи. Повтор с тем же ID для другого проекта отклоняется. При таймауте и рестарте сверяется ref исходного репозитория. Успешный результат для A никогда не добавляется в видимую доску B.

При переименовании обновлять отображаемое owner/name после проверки repository ID. При переносе между аккаунтами, изменении установки или отзыве прав блокировать запись до проверки новой установки. Архивирование локального проекта не стирает снимки его старых задач.

## Серверные контракты (предложение)

| Метод и маршрут | Назначение |
| --- | --- |
| `GET /api/github/repositories` | Пагинированный/поисковый список доступных текущей установке репозиториев; публичные метаданные без токенов |
| `POST /api/github/repositories/resolve` | Разобрать GitHub URL, найти репозиторий среди разрешённых App, проверить ограничения; без подключения и записи в GitHub |
| `GET /api/github/repositories/:repositoryId/branches` | Список доступных веток проверенного репозитория для выбора базы |
| `GET /api/projects` | Подключённые проекты и состояние доступа |
| `POST /api/projects` | Подключить проверенный repository ID с базовой веткой |
| `PATCH /api/projects/:projectId` | Изменить настройки будущих задач или архивировать локальное подключение |
| `GET /api/tasks?projectId=...` | Только задачи указанного проекта; при отсутствии ID — понятная ошибка, без смешивания досок |
| `POST /api/tasks` | `{ projectId, requestId, title }`; сервер создаёт задачу и ветку в зафиксированном проекте |
| `POST /api/tasks/:id/branch/retry` | Повтор в проекте сохранённой задачи; выбранная в UI доска не влияет |
| `POST /api/tasks/:id/column` | Сохранить колонку задачи, не меняя проект |

Структура и названия маршрутов могут уточняться при реализации, но правила изоляции проектов обязательны. Полученный от браузера repository ID допустим только после серверной проверки доступа; owner/repo из непроверенного запроса не являются разрешением на операцию. Ссылка разбирается локально с фиксированным GitHub host; не делать fetch по произвольному URL (защита от SSRF).

## Проверки

При реализации: `npm run check`, `npm test`, `git diff --check`; при изменении UI — обычный и узкий экран. Новые тесты должны проверять результат, а не зеркалить внутренние функции.

Сценарии: список более 100 репозиториев; поиск; repo URL с `.git`; недопустимый host/порт/credentials; подмена repository/installation/project ID; повторное подключение; default branch не main; empty/archived repo; 401/403/404/429/5xx; отзыв прав между подключением и созданием; смена A→B во время запроса; две вкладки; устаревший GET A после ответа B; один request ID в разных проектах; рестарт с незавершённой задачей A при открытом B; миграция прежних задач; обновление базы; отсутствие лишних write scopes.

По выбору пользователя реальный рабочий пример пока один — habit-tracker. Изоляция двух репозиториев проверена автоматическими fixtures; второй реальный проект (сайт театра) отложен. Перед внешней записью — конкретное разрешение на выбранный repo и тестовую операцию. Создание репозитория `task-manager-demo` ранее отклонено автоматической проверкой до подтверждения параметров; действие не выполнено и не должно обходиться другим каналом.

Код теперь покрывает несколько проектов: каталог с пагинацией, URL и ID, токены с отдельными scopes, смену во время генерации, устаревшие ответы доски, повтор/рестарт и миграцию JSON. Исходные 37 тестов расширены; окончательные результаты фиксируются ниже после проверок. Схема SQLite покрыта отдельными тестами, JSON остаётся действующим хранилищем.

## Что потребуется от команды

Для разработки с заглушками ничего дополнительно не нужно. Для настоящей проверки владелец выбирает в установке GitHub App репозитории-примеры (Only select repositories). Не нужно выдавать доступ всем текущим и будущим репозиториям. Регистрация новой App или создание нового PEM для каждого проекта одного аккаунта не требуются.

При работе с репозиторием другого владельца App должна быть доступна для установки на тот аккаунт и установлена его владельцем. Текущая App ограничена аккаунтом karinalien; расширение области установки — отдельная настройка с подтверждением. Роли Task Manager, вход пользователей и фильтрация по пользовательскому GitHub-доступу останутся будущим этапом.

## Передача

Следующий шаг после завершения сквозной проверки — отдельная задача подключения SQLite к API/переноса JSON, когда команда решит начать её.
