# Работа с Task Manager

Общайтесь по-русски. Учебный проект Карины и Софии: канбан-доска с LLM-планированием и GitHub. Codex помогает разработке; встроенный AI-исполнитель продукта — отдельная будущая функция.

## Порядок работы

- Перед работой, особенно после перерыва или в новом чате: проверьте `git status --short`, текущую ветку, `git branch -vv`, выполните `git fetch --all --prune`; сравните изменения с remote и базой PR, учтите коммиты коллеги, перечитайте изменившиеся инструкции и план. При недоступной сети сообщите, что удалённая актуальность не подтверждена.
- Каждую крупную задачу выполняйте в отдельной ветке и одном PR. Найдите и продолжите подходящую незавершённую ветку; если её нет — создайте `codex/<task-id>-<description>` от проверенной актуальной базы. Слитые ветки не переиспользуйте; задачи и чужие незавершённые изменения не смешивайте. Подробности — в WORKFLOW.
- Для нескольких модулей или интеграции создайте `docs/plans/<task-id>.md`; для мелкой правки достаточно плана в чате. Обычные решения принимайте самостоятельно в рамках запроса, изменения делайте минимально достаточными.
- Сохраняйте чужую работу; не применяйте слепой `git pull`. Коммит и push — по поручению; force-push, merge и публичное развёртывание — только по соответствующему запросу.
- Не запускайте дополнительных агентов автоматически. При явном запросе на делегирование разделите задачи и закрепите файлы за исполнителями.

## Ограничения проекта

- HTML/CSS, обычный JavaScript и встроенные модули Node.js, без сборки и npm-зависимостей. Не добавляйте фреймворки, SDK, новую БД или масштабную перестройку попутно с небольшой задачей.
- JS: 4 пробела, двойные кавычки, точки с запятой. Сохраняйте русский интерфейс и адаптивность.
- GitHub и необязательный `AI_API_KEY` — в серверном `.env`; endpoint/model/generation/timeoutMs — в корневом `ai.config.json`. Общий LLM-клиент — `lib/llm.js`. Setup создаёт конфиги только при отсутствии; личные конфиги и прежний `ai-api.js` не перезаписывайте. История старых настроек — в README.
- Секреты остаются на сервере: не помещайте их в браузерные файлы, примеры, логи и Git. Текущий сервер не считайте готовым к публичному размещению. При частичной настройке `DEMO_USERNAME`/`DEMO_PASSWORD`/`SESSION_SECRET` API должен оставаться закрытым.
- Qwen оформляет только `title`/`description`/`questions` (0–3); исходный input и уточнения храните отдельно. Ветку формирует код из выбранного типа и ID только после явного подтверждения карточки; повтор генерации ветку не создаёт.
- Выводите пользовательский текст и ответы LLM безопасно, без прямой вставки в `innerHTML`; валидируйте ответ до изменения состояния и внешних действий.
- Выбирайте проект через `ProjectService` и явный `projectId`, без общего активного repo для всех вкладок. Задачи/проекты — JSON v2, сотрудники/события — SQLite через `lib/workspace.js`; перенос задач в SQLite — отдельная задача.

## Проверка и завершение

- Выполните `npm run check` и `git diff --check`; при изменении поведения — `npm test` и соответствующие сценарии WORKFLOW. Добавляйте соразмерные тесты результата и ошибок, а не формулировок документации.
- В базовых тестах используйте заглушки GitHub/LLM. Реальные `npm run github:check` и `npm run llm:check` выполняйте отдельно; сообщайте только действительно проверенное — синтаксис не доказывает работу UI или модели.
- При изменении возможностей обновите PROJECT, статусы REQUIREMENTS и тематические документы. Указывайте дату и проверенную ветку/коммит; отличайте частичную функцию от готового блока, push от merge в main и прежние проверки от новых. Историю оставляйте в плане задачи.
- В review ищите воспроизводимые дефекты, потерю данных, регрессии, секреты и нарушения критериев; указывайте файл, строку, сценарий и последствия. Пожелания стиля не выдавайте за блокирующие ошибки.
- Завершая, сообщите результат, проверки, ограничения и следующий шаг, если он нужен.
