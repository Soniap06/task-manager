# Task Manager

Учебная канбан-доска с подключаемыми GitHub-проектами. Выберите существующий репозиторий, создайте задачу — сервер подготовит ТЗ через локальную LLM и создаст в этом репозитории ветку через GitHub App. Доски разных проектов независимы; переключение не меняет назначение старых задач.

## Локальный запуск

Нужны Git и Node.js 24 (`nvm use` при наличии nvm). Внешних npm-зависимостей и сборки нет.

```bash
npm run setup
npm run check
npm test
npm start
```

`setup` создаёт `.env` из [.env.example](.env.example), только если файла ещё нет. Заполните серверные настройки:

| Переменная | Значение |
| --- | --- |
| `GITHUB_APP_ID` | ID GitHub App |
| `GITHUB_INSTALLATION_ID` | ID установки App на рабочий аккаунт |
| `GITHUB_PRIVATE_KEY_PATH` | Абсолютный путь к RSA PEM или путь относительно корня проекта |
| `LM_STUDIO_MODEL` | Идентификатор загруженной модели, например `qwen/qwen3.5-9b` |
| `LM_STUDIO_ENDPOINT` | Обычно `http://127.0.0.1:1234/v1/chat/completions` |
| `AI_API_KEY` | Необязательный серверный Bearer-ключ облачного API ИИ |
| `PORT` | Порт приложения, по умолчанию 3000 |
| `DATA_DIR` | Каталог JSON-хранилища, по умолчанию `.data` |

Откройте `http://127.0.0.1:3000` (или настроенный порт). Запустите HTTP-сервер LM Studio на localhost и загрузите модель с поддержкой JSON schema. `ai-api.js` — сохранённый прежний клиент, интерфейс его больше не загружает. Owner/repo и базовая ветка теперь выбираются в UI, а не в `.env`.

## Подключение и смена проекта

1. Перейдите на страницу «Проекты» в верхнем меню и откройте «Подключить существующий репозиторий».
2. Нажмите «Обновить репозитории App» либо вставьте GitHub-ссылку и нажмите «Найти по ссылке».
3. Выберите доступный репозиторий и базовую ветку. По умолчанию берётся фактическая основная ветка GitHub; при необходимости доступны подсказки с другими ветками.
4. Нажмите «Подключить». Само подключение не создаёт GitHub-веток.
5. Нажмите «Открыть доску задач» и создавайте задачи. Ветка имеет вид `feat/task-<uuid>-<slug>` (также `fix/` или `chore/`), её ссылка появляется только после подтверждённого успеха. На доске видны название задачи и кнопки переноса; нажмите на карточку, чтобы открыть репозиторий, ветку, статус, критерии приёмки и шаги. Окно закрывается кнопкой «Закрыть» или Escape.

В списке находятся только репозитории, к которым GitHub App имеет доступ. Если нужного нет, откройте «Настроить доступ на GitHub», добавьте нужный репозиторий в установку и обновите список. Вставка URL не расширяет права App. Пустой репозиторий без первого коммита и архивный репозиторий не подходят для создания веток.

Список «Проект и репозиторий» на странице «Проекты» выбирает рабочий проект без перезапуска сервера. Там же находятся управление подключением, доступом App и базовой веткой. На доске отображаются текущий проект и задачи; ссылка на ветку остаётся в карточке задачи. Выбор сохраняется отдельно для вкладки. Задача, запущенная в A, останется в A, даже если во время генерации открыть B. Настройка базовой ветки влияет только на новые задачи; повторы используют сохранённые параметры. «Отключить проект» сохраняет историю и запрещает новые внешние операции; удалённый репозиторий и его ветки не удаляются. Подключение можно восстановить.

Генерация может занять до двух минут. При ошибке карточка остаётся на доске с причиной и кнопкой «Повторить». При потерянном ответе сначала обновите доску: операция могла завершиться. Request ID и точное имя ветки защищают от дублирования. Перенос карточки сохраняется и не создаёт PR или новую ветку. Локальный checkout разработчика не переключается.

Рабочий пример: [трекер привычек](https://github.com/karinalien/habit-tracker). Это отдельный стартовый проект с тестами; создание ветки не означает автоматического выполнения её задачи. Сайт театра оставлен будущим примером.

## GitHub App

App требует Contents: Read and write и Metadata: Read-only. Установите её на рабочий аккаунт через Only select repositories; не нужно предоставлять доступ ко всем проектам. Пользовательский OAuth не используется. Подписанный webhook реализован отдельно; для создания веток его включать не требуется. После изменения доступа используйте:

```bash
npm run github:check
```

Команда получает список доступных App репозиториев, не создаёт веток и не выводит токены. Для операций записи сервер выдаёт отдельный временный токен с ограничением конкретным repository ID. PEM и токены остаются на сервере. `.env`, папка `github-app-keys/` и `.data/` игнорируются Git и не раздаются HTTP-сервером. Для нового окружения предпочтительно хранить PEM вне проекта.

Первый этап рассчитан на одну установку App одного аккаунта и любое число разрешённых ей репозиториев. Несколько аккаунтов/организаций и роли — следующие этапы. Необязательный вход с одним серверным логином описан ниже. Текущая App доступна для установки только на аккаунт karinalien. GitHub Pages не запускает backend; публичное размещение потребует авторизации пользователей.

## Данные и подготовленная БД

Сейчас API хранит проекты и задачи в `DATA_DIR/tasks.json`, версия 2, с атомарной заменой файла и блокировкой второго процесса. Прежний формат версии 1 мигрируется с резервной копией `tasks.json.v1-backup`; задачи без подтверждённых project/repository/installation ID попадают в архив без внешних операций, а не переназначаются текущему проекту.

SQLite инициализируется автоматически при запуске сервера; отдельно схему можно подготовить командой:

```bash
npm run db:init
```

Сервер использует `DATA_DIR/task-manager.sqlite` для сотрудников и событий, включая таблицу дедупликации webhook. Проекты для FK событий отражаются из JSON. **Рабочие задачи остаются в JSON; таблица tasks в SQLite пока заготовка.** Повторная инициализация не стирает данные. Подробности полей, capacity и следующей миграции: [DATABASE.md](docs/DATABASE.md). В Node.js 24 встроенный `node:sqlite` выдаёт штатный ExperimentalWarning.

Это локальный однопроцессный сервис без общей БД команды. Разные локальные серверы имеют независимые данные. Сохраняйте резервные копии JSON и SQLite. Создание PR, автоматическое review, редактирование профилей и планировщик пока не реализованы.

## Команда, вход и события

В навигации доступны «Сотрудники», «События» и «Профиль». Сохранён интерфейс новых страниц Софии; поиск, перетаскивание и выбор исполнителя добавлены на доску с GitHub App. Подробное ТЗ по-прежнему видно только в диалоге карточки. Три начальные карточки команды (Карина, София, Qwen) — демонстрационные данные; AI-исполнитель ещё не выполняет задачи. Ёмкость измеряется в часах за спринт, назначенные задачи показаны отдельным числом без вычисления часов.

Для входа заполните в `.env` DEMO_USERNAME, DEMO_PASSWORD и SESSION_SECRET (не менее 32 случайных символов) и перезапустите сервер. Все прикладные API будут требовать подписанную HttpOnly cookie. Для профиля Карины используйте логин `karina`, Софии — `sofia`; произвольному логину чужой профиль не назначается. Если все три поля пустые, сохраняется локальный режим без входа; частичная настройка закрывает API до исправления. Пароли и секреты не имеют фиксированных значений по умолчанию. Роли и полноценная регистрация ещё не реализованы.

Webhook: `POST /api/webhooks/github`, секрет GITHUB_WEBHOOK_SECRET, события push/pull_request/pull_request_review. Событие принимается только для подключённого repository.id, повторы доставки исключаются. Список событий запрашивается с явным projectId. Приложение слушает loopback: публичный приём webhook требует отдельной настройки, она не выполнялась.

`POST /api/ai/generate-task` даёт предпросмотр ТЗ через общий генератор, без сохранения карточки и GitHub-записи. Облачный Qwen подключается через общий клиент: LM_STUDIO_ENDPOINT задаёт полный Chat Completions endpoint, LM_STUDIO_MODEL — модель, AI_API_KEY — серверный ключ. Прежние QWEN_BASE_URL/QWEN_MODEL/QWEN_API_KEY не читаются; перенесите настройки в общие поля. Требуется поддержка JSON schema; реальный облачный API не проверен. Ограничения запуска и данные прежней версии Софии: [DEPLOYMENT.md](DEPLOYMENT.md). Истории объединения: [план интеграции](docs/plans/INTEGRATE-sofia.md).
